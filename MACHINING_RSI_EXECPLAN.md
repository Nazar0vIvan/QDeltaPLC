## Purpose / Big Picture


The user will be able to prepare a selected generated chamfer path for one internal hole edge, execute its three central phases through KUKA RSI, and subsequently enable a bounded force-dependent retreat. KRL will perform HOME, staging and straight auxiliary transfers. Generating a path, selecting it, preparing a job and running the preview will never start hardware motion.

The first useful result is an offline prepared nominal job with its actual timing, phase boundaries, calibrated poses and preparation errors visible to the application. The next result is a complete nominal execution contract between the application and controller. Force processing follows with correction disabled; force-driven movement is activated only after its configuration and physical response have been established.

The agreed target is KR10 R1420, KR C4, KSS 8.3.31, RSI 3.3, T1, Cartesian POSCORR, relative corrections and a 4 ms cycle. Cyclic processing remains in Windows Qt. No automatic 12 ms fallback is included. The cutter is a cylindrical burr; the workpiece is steel, with a nominal approximately 0.5 mm, 45-degree chamfer. These descriptive values do not override a saved path's actual settings.

## Surprises & Discoveries


The current hardware path is unrelated to the saved chamfer motion. Evidence: RsiDevice::generateTrajectory in src/network/rsi/rsidevice.cpp constructs hardcoded cylinder/plane geometry and calls RsiPath::lin. RsiDevice::setForce only scales and stores Fz; it does not change motion.

Stop is incomplete on the wire. Evidence: RsiTxFrame in src/network/rsi/rsiprotocol.h has shouldStop, but RsiProtocol::encode writes only RKorr and IPOC. tickMotion can set shouldStop with the last nonzero increment; this must not become the new completion behavior.

The existing resource and supplied reference use different stop tags. Evidence: resources/files/RSI_EthernetConfig.xml uses Flags.ShouldStop, whereas the strategy's supplied reference uses Stop. Neither spelling proves a deployed graph. Milestone 5 must choose and document one matching contract, then update all affected consumers together.

Exact motion boundaries need explicit execution ownership. Evidence: ChamferMotion::evaluate in src/pathgeneration/chamfer/chamfermotion.cpp advances its phase with time >= the next boundary. The central final pose is correctly evaluated at boundaries[5], but its returned phase is TransferOut. Hardware preparation must retain that pose as the central endpoint.

High-frequency sensor reception is already available, but the display/recorder path is unsuitable as the control clock. Evidence: FtsDevice::onReadyRead emits dataSampleHFReady before batching, derives timestamp from rdt_sequence using a fixed 7,000 Hz assumption, and drains pending datagrams in a while loop. The shared ControlIO thread makes bounded receive work necessary for RSI deadlines.

Saved-path compatibility also includes preview availability. Evidence: SceneMachining::updateCompatibility in src/scene/scenemachining.cpp:247 first compares calibration revisions, then checks m_robotAvailable. OccController::synchronizeMachiningReadiness at src/3d/occcontroller.cpp:175 supplies that availability from viewer/robot readiness. Stage A can reuse this conservative existing gate, but neither compatible() nor a loaded preview establishes real-controller TOOL/BASE/session readiness.

There is an existing metadata route for a Scene-owned preparation QObject. Evidence: src/CMakeLists.txt extracts RoboCrapScene metatypes, and RoboCrapBackend links Scene for QML_FOREIGN registration in src/backendqmltypes.h. A preparation coordinator compiled in Scene can follow that route without depending on Devices. Executable composition can still connect its numerical result to RSI.

Milestone 1 found aboutToQuit stopping the hub before later application callbacks: the original src/main.cpp:84 connected DeviceHub::stopAll before constructing SceneMachining. Stage A moves that connection after the new preparation shutdown callback. Result dispatch now stops and the worker finishes before hub stopAll; coordinator destruction also waits without relying on a running I/O event loop.

Boundary validation can reuse the saved evaluator without regenerating IK or changing feeds. Evidence: PreparedChamferJob::create validates all eight saved phase boundaries and compares their evaluated FK TCP positions/rotations with the retained points using existing KR10 tolerances. It uses boundaries[2..5] for central times and explicitly labels the evaluated terminal boundary LeadOut. The source ChamferMotion stays immutable; no 4 ms target vector is generated in Stage A.

The saved timer's scalar waypoint speeds are temporary. Evidence: MotionTimer::timeCentral creates local distance/speed vectors, retains timestamps and cubic joint velocities, then applies centralTimeScale. There is no retained analytic arc-length law to reuse. Milestone 3 therefore uses the saved timed FK reference only to recover progress within each known analytic parameter interval. The resulting target is an analytic Cartesian frame, not the interpolated FK frame.

Arbitrary geometric knots can be extremely close to a 4 ms validation subdivision or the terminal time. Numerical rate differencing on such tiny gaps can magnify roundoff. Milestone 3 retains those knots for geometric/IK checks, removes duplicate validation times and merges intervals below 100 us for rate estimates. Stored controller-clock targets and exact phase timestamps are unaffected.

Milestone 4 research found a real documentation boundary. KUKA's supplied KST RSI 3.3 V4 manual (17.06.2016), pages 16-19, establishes CCS at TCP, selectable reference orientation and accumulation, but not the simultaneous A/B/C composition algorithm. Pages 23, 65, 73 and 77 describe object/overall correction monitoring without full parameter semantics. The local manuals contain no POSCORR/POSCORRMON object help, and no KUKA/WorkVisual installation was found in the two standard Program Files directories. Third-party forum suggestions were not adopted as a controller contract.

The user subsequently settled the implementation contract explicitly: A/B/C add directly to the starting TCP Euler angles. The orientation mapping is no longer a missing fact for software implementation. It requires a continuous absolute Euler representation, not a matrix-derived rotation delta or a separate correction-frame rotation. The existing rot2euler uses asin near pitch +/-90 degrees and returns a zero-C gauge at singularity; the local encoder uses stable atan2 pitch and the preceding serialized attitude to maintain branches/gauge, without changing the global geometry helpers. A future session must validate the controller's initial Euler family because rotation-matrix equality alone does not ensure identical direct-addition behavior.

The correction-limit investigation found no local RsiElements.chm. The supplied manual identifies clamping versus stopping but does not define the monitor formulas/ranges. A first-hand RSI 3.x/KSS 8.3 hardware report provides supporting evidence that POSCORR translation bounds act on cumulative correction: small per-cycle increments still hit an object limit. Its numerical settings and other session choices were not adopted. The user then explicitly clarified MaxTrans and MaxRotAngle as maximum allowable changes of X/Y/Z and Euler A/B/C. This closes the software formula question: compare each cumulative component relative to the starting TCP, not a translation norm or principal rotation magnitude. Actual parameter ranges, accepted values and installed graph remain unverified equipment facts.

## Settled Behavior and Clarification Policy


Execute one saved edge with KRL HOME -> P_s,in by PTP, fixed-attitude LIN to the clear lead-in start, one continuous PC-controlled LeadIn/Machining/LeadOut RSI interval, then normal-completion-only LIN to P_s,out and PTP HOME. The staging origins may coincide while orientations differ. Do not blend KRL/RSI handoff corners or split the central motion into independent sessions.

During Machining, define n = R_nom * UnitZ and r >= 0 in millimetres. Command p_cmd = p_nom + r*n and R_cmd = R_nom. Retreat begins at zero, increases under excessive selected force and remains after force falls. Nominal path progress continues. No tangential force-dependent slowdown, pause-and-relieve, force-driven orientation change or automatic finishing pass is included. LeadIn has zero retreat. LeadOut carries the displacement, makes no new force-feedback decisions and removes the displacement smoothly after proven clearance. Abort bypasses this normal exit and must not automatically return anywhere.

Use the full target difference delta_p = p_cmd[k] - p_cmd[k-1]. This includes r[k]*n[k] - r[k-1]*n[k-1]; delta_r*n alone loses the motion caused by a changing normal. The previous commanded/encoded target is execution state. Replacing it with measured RIst and repeatedly integrating target-minus-measured is a different feedback controller and is outside this strategy.
