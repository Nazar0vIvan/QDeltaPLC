# Математика и подготовка анимации KR10: обзор литературы и кода

Дата: 12 октября 2026. Исследование, не план реализации. Производственный код не изменён; новые сборки и измерения альтернативных реализаций не выполнялись. Числа RoboCrap ниже пересчитаны из существующего отчёта двух запусков Debug.

## Вывод для этого проекта

Для KR10 предпочтительный следующий кандидат — вычисление положения робота непосредственно по времени кадра: существующий закон расстояния, существующая обратная зависимость длины, исходная геометрия и ориентация, аналитическая IK выбранной конфигурации, FK звеньев. Не требуется подбирать интервалы для линейной интерполяции углов. Соответствующая аналитическая IK уже реализована и её измеренная средняя стоимость мала относительно периода обновления анимации.

Это не означает, что можно удалить предварительные проверки и просто вызывать текущую solveIK с предыдущим кадром. Заранее должны быть определены допустимая ветвь решения и непрерывное представление углов с полными оборотами; должны сохраниться проверки достижимости и ограничений. Их стоимость ещё не измерена для предлагаемого представления. Рекомендация архитектурная, а не обещание времени Generate.

Вариант «один раз построить сплайны углов и затем вычислять только полиномы» также математически корректен, но вносит дополнительную погрешность TCP. Для одного аналитически решаемого KR10 необходимость этого дополнительного приближения пока не подтверждена.

## Что проверено в RoboCrap

- src/pathgeneration/chamfer/chamfercentralmotion.cpp: расчёт длины по времени, затем progressAtDistance, затем исходный evaluatePhase.
- src/pathgeneration/chamfer/chamferarclength.cpp: заранее построенная кусочно-квинтическая обратная зависимость. Запрос параметра использует двоичный поиск по узлам и вычисление полинома, а не новый поиск корня.
- src/pathgeneration/chamfer/chamferpath.cpp: исходные положения и ориентации; аналитические производные положения по параметру.
- src/3d/robot/kinematics/kr10kinematics.cpp: solveIK выбирает конфигурацию из currentQ, вычисляет первые три угла геометрически, последние три из относительной ориентации, затем проверяет FK. Используются atan2, acos, арифметика и выбор полных оборотов. Итерационного уточнения углов нет.
- src/pathgeneration/chamfer/chamfercentralvalidation.cpp: исходные интервалы не более 4 мс; четверти интервалов дают приблизительно 1 мс между сохраняемыми положениями. Проверяется также ошибка линейной интерполяции углов.
- src/pathgeneration/chamfer/chamfermotion.cpp: на пяти декартовых участках воспроизведение линейно интерполирует сохранённые углы. HOME использует отдельную квинтическую функцию времени.
- src/scene/scenemachining.cpp: таймер обновления 16 мс, время берётся из монотонных часов. Это период запроса обновления, не гарантия фактической частоты кадров.
- src/3d/occcontroller.cpp, src/3d/robot/robotpreviewstate.cpp: полученные углы проходят FK для размещения звеньев.
- src/pathgeneration/chamfer/chamfercartesiansampler.cpp: RSI получает аналитические TCP, но для конфигурации и дополнительных проверок всё ещё читает сохранённые точки анимации.

Уточнение терминов: currentQ в этой конкретной аналитической IK — опорные углы для выбора конфигурации и полных оборотов. Называть их «начальным приближением итерационного решателя» неверно.

## Геометрия, время и кинематика — три разные зависимости

Обозначения: \(u\) — безразмерный параметр фазы, \(p(u)\) — положение TCP в мм, \(R(u)\) — матрица его ориентации. \(s\) — длина, пройденная началом координат TCP вдоль кривой, в мм. \(t\) — время от начала фазы, в секундах.

Длина определяется геометрией:

\[
s(u)=\int_0^u \|p'(\xi)\|\,d\xi.
\]

Штрих — производная по параметру; \(\xi\) — переменная интегрирования. Обратная функция \(u(s)\) в RoboCrap уже аппроксимирована квинтическими полиномами. Это приближение остаётся и при аналитической IK; называть весь расчёт абсолютно точным нельзя.

Для подвода: \(L\) — его полная длина, \(f\) — доля длины разгона, \(V_m\) — скорость обработки. Тогда:

\[
a=\frac{V_m^2}{2fL},\qquad t_a=\frac{2fL}{V_m},
\]

\[
s(t)=
\begin{cases}
\tfrac12 at^2,&0\le t\le t_a,\\
fL+V_m(t-t_a),&t_a<t\le T.
\end{cases}
\]

Здесь \(a\) — касательное ускорение, \(t_a\) — длительность разгона, \(T=t_a+(1-f)L/V_m\) — полная длительность подвода. При \(f=1\) второй участок отсутствует. Отвод содержит постоянную скорость, затем торможение. Для полного симметричного перемещения с остановками на обоих концах добавляется участок торможения; для короткой дистанции профиль становится треугольным.

Матрица положения и ориентации TCP в системе BASE обозначена \(H_{\rm TCP}(u)\). Постоянная матрица \(C\) задаёт TCP относительно фланца. Цель для IK:

\[
H_{\rm flange}(u)=H_{\rm TCP}(u)C^{-1}.
\]

После выбора непрерывного решения IK получаем шесть функций \(q_i(u)\), где индекс \(i=1,\ldots,6\) обозначает сочленение. Воспроизведение вычисляет \(q_i(u(s(t)))\). Это композиция уже определённых функций, не обязательный массив положений через 1 мс.

Такое разделение описывает [Modern Robotics, главы 9.1–9.2](https://modernrobotics.northwestern.edu/nu-gm-book-resource/9-1-and-9-2-point-to-point-trajectories-part-2-of-2/). В [Orocos KDL](https://raw.githubusercontent.com/orocos/orocos_kinematics_dynamics/master/orocos_kdl/src/trajectory_segment.cpp) оно непосредственно выражено вызовом геометрии из закона времени в Trajectory_Segment::Pos. KDL содержит и [полный трапецеидальный профиль](https://raw.githubusercontent.com/orocos/orocos_kinematics_dynamics/master/orocos_kdl/src/velocityprofile_trap.cpp), и [половинный профиль разгона/торможения](https://raw.githubusercontent.com/orocos/orocos_kinematics_dynamics/master/orocos_kdl/src/velocityprofile_traphalf.cpp). Их правила ограничения скорости не следует автоматически переносить вместо наших заданных параметров.

## Что обеспечивает непрерывность движения

Непрерывное положение обозначают \(C^0\); непрерывные положение и скорость — \(C^1\); непрерывные положение, скорость и ускорение — \(C^2\).

Трапецеидальная скорость непрерывна, но её производная — ускорение — скачком меняется при переключениях. Поэтому требование сохранить именно трапецеидальный закон несовместимо с требованием непрерывного ускорения на всех переключениях. Для последнего требуется другой закон, например S-образный. Это не повод менять заданный закон ради анимации.

Пусть \(g(u)=\|p'(u)\|>0\). Достаточные условия для непрерывной скорости сочленений:

1. Положение и ориентация TCP имеют непрерывные первые производные по \(u\), в том числе в местах соединения фаз с ненулевой скоростью, после согласования параметризации.
2. Длина имеет монотонную обратную зависимость.
3. Выбрана непрерывная ветвь IK, и робот не проходит кинематическую особенность. Кинематическая особенность — конфигурация, в которой матрица Якоби теряет ранг; связь скоростей перестаёт быть обратимой для произвольного движения TCP.
4. Полные обороты учитываются непрерывно: переход от 179 к 181 градусу не заменяется переходом от 179 к −179.
5. Закон времени имеет непрерывную скорость.

Это условия на функции и выбранное решение, а не на число сохранённых кадров. Матрица Якоби связывает скорости сочленений с линейной и угловой скоростями инструмента; см. [Modern Robotics, 5.1.1](https://modernrobotics.northwestern.edu/nu-gm-book-resource/5-1-1-space-jacobian/) и [5.3](https://modernrobotics.northwestern.edu/nu-gm-book-resource/5-3-singularities/).

Непрерывность не равна соблюдению ограничений: возле особенности углы могут изменяться непрерывно, но слишком быстро. Нельзя заявлять допустимость только по внешней гладкости кривой TCP.

Линейная интерполяция углов, используемая сейчас, непрерывна по положению, но обычно имеет скачки скорости в узлах. Уменьшение интервалов уменьшает погрешность, но само по себе не превращает её в \(C^1\)-функцию. [Документация ROS joint_trajectory_controller](https://control.ros.org/jazzy/doc/ros2_controllers/joint_trajectory_controller/doc/trajectory.html) явно различает линейную, кубическую и квинтическую интерполяцию по уровню непрерывности.

## Дополнительный вывод из текущей формулы ориентации подвода

Это собственное алгебраическое следствие прочитанного кода, не результат измерения и не новая реализация.

Пусть \(k\) — единичная наружная ось отверстия; \(r\) — единичное радиальное направление при текущем параметре эллипса; \(x=r\times k\); \(\alpha\) — угол фаски. Матрица со столбцами \(x,-k,r\) обозначена \(R_0\). В коде она соответствует clearRotation.

Ориентация TCP для обработки в этой же точке равна:

\[
R_{\rm machining}=R_0 R_x(-\alpha),
\]

где \(R_x(\beta)\) — поворот на угол \(\beta\) вокруг локальной оси X. Обе ориентации имеют общую ось X. Поэтому текущая сферическая интерполяция кватернионов с весом \(w\) математически эквивалентна:

\[
R_{\rm TCP}=R_0R_x(-\alpha(1-w)).
\]

Для подвода \(w=1-\sin(\pi u/2)\), а угловой параметр вокруг отверстия равен \(-\Delta\theta\cos(\pi u/2)\), где \(\Delta\theta\) — заданный угловой охват. Радиальное направление вычисляется с учётом направления обхода m_direction.

Это показывает, что закон изменения ориентации здесь уже определён простой функцией. Не нужно придумывать интерполяцию ориентации между произвольными кадрами. Равенство дано в вещественной арифметике; замена кватернионного кода не выполнялась и потребовала бы отдельной проверки численной эквивалентности.

## Сравнение подходов

| Подход | Подготовка | Вычисление положения для кадра | Точность и ограничения |
|---|---|---|---|
| Текущая плотная сетка и линейная интерполяция углов | IK и многочисленные FK для тысяч временных точек и повторных конфигураций | Поиск соседних точек, линейная интерполяция, FK | Контролируется выборочная ошибка TCP; скорости обычно разрывны в узлах |
| Разреженная сетка с той же линейной интерполяцией | Подбор интервалов по ошибке | То же, меньший массив | Устраняет часть затрат, но не причину разрыва скоростей |
| Аналитическая поза и аналитическая IK для времени кадра | Геометрия, закон времени, выбор непрерывной конфигурации, предварительные проверки | Длина, обратный параметр, исходная поза, IK, FK | Не добавляет ошибку интерполяции углов; сохраняет ошибки исходной численной модели; требует корректной ветви |
| Кубический/квинтический сплайн углов по параметру пути | Вычисление опорных углов и производных, коэффициентов, проверка ошибки | Вычисление шести полиномов и FK | Непрерывность задаётся условиями сопряжения; декартова траектория приближённая |
| Глобальные полиномы Чебышёва для углов | IK в узлах, подбор степени и проверка остатка | Шесть полиномиальных разложений и FK | Возможна высокая точность на регулярном участке; нужная степень заранее не фиксирована |
| Дифференциальная IK и численное интегрирование | Начальная конфигурация и формулы производных | Решение системы с Якобианом, шаг интегратора, коррекция | Ошибка интегрирования накапливается; труднее произвольный переход по времени |
| TOPPRA | Выбирает допустимый быстрый закон времени на заданном пути | Вычисление полученной траектории | Решает иную задачу: может изменить требуемую трапецеидальную скорость |
| Ruckig | Строит движение между заданными состояниями с ограничением рывка | Вычисление готовой траектории по времени | Сам по себе не сохраняет произвольную заданную декартову кривую при планировании шести углов |
| PH-кривые | Требуют специального класса геометрии либо аппроксимации исходной | Вычисление специальной кривой и её параметра | Удобная длина не устраняет роботную IK; замена нашей геометрии не обоснована |

### Аналитическая IK для каждого кадра

Работа [Elias, Wen, IK-Geo](https://arxiv.org/pdf/2211.05737), опубликованная позднее в Mechanism and Machine Theory, 2025, DOI 10.1016/j.mechmachtheory.2025.105971, показывает семейства роботов, допускающие решение без итерационного поиска. Изучены разделы о геометрическом разложении и таблица V в доступной версии arXiv v3. [Репозиторий авторов](https://github.com/rpiRobotics/ik-geo) содержит реализации и примеры. Для RoboCrap это подтверждение применимости подхода, не основание заменить уже работающую специализированную IK сторонней библиотекой.

В таблице V для подготовленных моделей со сферическим запястьем приведены, например, 4,527 мкс для MEX и 2,425 мкс для Rust на i7-3770K. Эти результаты нельзя переносить на наш Debug или сравнивать как прямое ускорение: различаются модели, языки, сборка и объём проверок.

В [CoppeliaSim moveToPose](https://manual.coppeliarobotics.com/en/sim/simMoveToPose.htm) поддержано движение объекта с IK и обработка каждого шага движения. Это пример вычисления кинематики во время симуляции, но его Ruckig-профиль не равен нашему закону подвода. Учебник [Kris Hauser, Robot Control](https://motion.cs.illinois.edu/RoboticSystems/RobotControl.html), раздел Cartesian commands, также описывает вычисление IK для текущей декартовой цели и отдельно необходимость проверять существование решения.

В [Pilz/MoveIt](https://raw.githubusercontent.com/moveit/moveit2/main/moveit_planners/pilz_industrial_motion_planner/src/trajectory_functions.cpp) есть и другой вариант: generateJointTrajectory создаёт временные отсчёты, вычисляет KDL-позу и последовательную IK, проверяет ограничения и сохраняет углы, скорости и ускорения. Следовательно, нельзя утверждать, что все симуляторы или промышленные планировщики используют только непосредственное вычисление для кадра.

### Предварительные сплайны углов

Кубический полином на участке задаётся углами и первыми производными на двух концах. Квинтический дополнительно задаётся вторыми производными. При согласованных граничных данных соседних участков получается соответствующая непрерывность. Это реализовано в [ROS QuinticSplineSegment](https://raw.githubusercontent.com/ros-controls/ros_controllers/noetic-devel/joint_trajectory_controller/include/trajectory_interface/quintic_spline_segment.h) и представлено в [Klamp't HermiteTrajectory](https://motion.cs.illinois.edu/software/klampt/latest/pyklampt_docs/Manual-Paths/).

Но построенный полином угла между опорными точками обычно не равен точной IK исходной позы. Сглаженный угол не доказывает точность TCP. Поэтому потребуется оценка ошибки и выбор числа коэффициентов/участков. Если заранее известна строгая верхняя граница четвёртой производной функции угла, остаток кубической интерполяции Эрмита можно ограничить величиной \(M h^4/384\), где \(M\) — эта граница, а \(h\) — ширина интервала параметра. Получение такой границы для композиции нашей геометрии и IK само является отдельной задачей; кроме того, потребуется связать ошибку углов с ошибкой TCP.

При сохранении трапеции предпочтительнее аппроксимировать углы как функции параметра геометрии, а закон времени применять отдельно. Иначе глобальное сглаживание ускорения в сплайне по времени может незаметно изменить требуемый профиль.

### Полиномы Чебышёва

Это вариант хранения шести функций углов коэффициентами вместо многочисленных кадров. Для аналитических функций при наличии подходящей комплексной области аналитичности ошибка убывает геометрически с ростом степени; см. [Trefethen / Chebfun, глава 4](https://www.chebfun.org/docs/guide/guide04.html). Это общее математическое основание, не опубликованный замер на нашем KR10.

Близкие особенности IK ухудшают сходимость; разрывы представления углов нужно устранить до аппроксимации. Подбирать степень и проверять точность всё равно придётся. Поэтому метод не даёт универсального заранее известного количества коэффициентов из длины и охвата подвода.

### TOPPRA и Ruckig

[Pham, Pham, 2018](https://arxiv.org/pdf/1707.07239), разделы II B–C, формулируют преобразование скоростей/ускорений вдоль пути и дискретизацию задачи ограничений. [TOPPRA](https://github.com/hungpham2511/toppra) предназначен для выбора временной параметризации. Если скорость уже задана пользователем, запускать оптимизацию времени ради отображения не нужно. Сами авторы обсуждают отличие ограничений в узлах от их выполнения между узлами.

[Berscheid, Kröger, RSS 2021](https://www.roboticsproceedings.org/rss17/p015.pdf), таблица III: Ruckig строил движение для семи степеней свободы в среднем за 19,8 мкс, наибольшее измеренное время — 123 мкс, на i7-8700K, один поток PREEMPT-Linux. Это время генератора состояний, без нашей геометрии и IK, не время подготовки отверстия. [Ruckig API](https://github.com/pantor/ruckig) поддерживает разовую подготовку calculate и вычисление at_time; это полезный пример представления траектории функцией. Добавлять ограничение рывка ради анимации означало бы менять поставленный закон движения.

### PH-кривые и CNC

[Farouki, Shah, 1996](https://doi.org/10.1016/0167-8396(95)00047-X) рассматривают PH-кривые, для которых параметрическая скорость и длина полиномиальны. Обратная зависимость параметра от длины при этом в общем случае всё равно требует решения монотонного полиномиального уравнения. Подробные геометрические свойства также показаны в [авторском обзоре CNC](https://faculty.engineering.ucdavis.edu/farouki/wp-content/uploads/sites/41/2013/02/Computer-numerical-control-algorithms.pdf).

Нельзя автоматически объявить текущую кривую начала координат TCP PH-кривой. Она включает поправку на фаску, осевое смещение и нормированные направления; это не просто исходный эллипс. Её замена потребовала бы геометрической аппроксимации. [Farouki, 2021](https://escholarship.org/uc/item/40t858d5) рассматривает быстрые численные CNC-интерполяторы для более общих кривых — подтверждение того, что численные вычисления параметра сами по себе не являются архитектурной ошибкой.

## Какие свойства можно подготовить один раз

При неизменных геометрии, калибровке и модели робота:

1. Аналитическое описание положения и ориентации TCP, константы размеров и направлений.
2. Длины фаз и коэффициенты обратной зависимости \(u(s)\).
3. Границы разгона/постоянной скорости/торможения и коэффициенты \(s(t)\).
4. Выбранное непрерывное решение IK вдоль геометрии и правила учёта полных оборотов.
5. Результаты проверки достижимости, ограничений углов и скоростей при этих настройках.
6. Если выбран сплайн-вариант — его коэффициенты и подтверждённые оценки ошибки.

Во время кадра неизбежно нужно вычислить текущее положение звеньев из времени. Разовая подготовка означает отсутствие повторного планирования, а не отсутствие арифметики при воспроизведении.

Для кадра в момент 0,053 с при нахождении на разгоне: вычисляется \(s=a(0,053)^2/2\); затем сохранённый \(u(s)\); затем evaluatePhase(LeadIn,u); затем преобразование TCP во фланец; затем шесть углов аналитической IK и FK звеньев. Никакие соседние моменты анимации не нужны. Значение 0,053 с здесь иллюстрирует произвольное время запроса, а не шаг разбиения.

Скорости также можно вычислять по производным функций, а не разностям кадров. Обозначим \(v=ds/dt\), \(a=dv/dt\), \(g=\|p'(u)\|\), \(g'=dg/du\). Тогда:

\[
\dot u=v/g,\qquad \ddot u=a/g-v^2g'/g^3,
\]
\[
\dot q_i=q'_i\dot u,\qquad
\ddot q_i=q''_i\dot u^2+q'_i\ddot u.
\]

Точка — производная по времени; штрих — по \(u\). Если углы в радианах, итоговые скорости в рад/с, ускорения в рад/с². На переключениях трапеции ускорение рассматривается отдельно слева и справа. Производные \(q_i\) можно получать дифференцированием аналитических формул IK либо через согласованный кинематический Якобиан. В текущем коде полная такая производная IK не реализована.

Это математическое выражение зависимости скоростей сочленений от геометрии и заданного закона движения. Наличие выражения не означает, что его максимум на всём пути известен: экстремумы и близость к особенности требуют отдельного исследования.

## Что всё равно требует проверки

Для нашей IK конкретно проверяются расстояние центра запястья от первой оси, допустимость аргументов acos, ненулевой sin(q5) во внутренней системе углов решателя, непрерывность выбранной конфигурации и пределы каждого сочленения. Угол q5 в формуле решателя учитывает модельные смещения; его нельзя без уточнения подменять отображаемым A5.

Равные позы TCP на концах замкнутой кривой не означают равные непрерывные углы: одно сочленение может выполнить полный оборот. Выбор решения лишь по предыдущему отображённому кадру ненадёжен при пропуске кадров или произвольном переходе по времени.

Проверить эти свойства для всех точек произвольной кривой только по двум концам нельзя. Возможны численный поиск экстремумов, продолжение решения с контролем, интервальные оценки. Последние ограничивают значения на целых диапазонах и могут потребовать деления диапазонов. Это проверка допустимости траектории, а не подбор кадров «чтобы казалось плавно». Разделение этих задач не устраняет стоимость проверки, но позволяет не связывать её с 1-миллисекундной сеткой отображения.

В существующем приложении RSI дополнительно опирается на точки анимации. При изменении представления углов эту зависимость необходимо заменить согласованным представлением конфигурации, не менять аналитические TCP и не обходить отдельные проверки RSI.

## Что можно сказать о быстродействии сейчас

При запросах через 16 мс за центральное движение 76,7722 с потребуется примерно 4800 вычислений положений робота. Это арифметическая оценка, без учёта задержек таймера, пауз и дополнительных запросов. Нынешняя успешная подготовка выполняет 76777 центральных IK, а все попытки — 164198.

При сохранении измеренной средней стоимости 70,24 мкс эти примерно 4800 вызовов IK заняли бы суммарно около 0,337 с процессорного времени, распределённого на всё воспроизведение. Один IK составил бы около 0,44% интервала 16 мс. Это не полный бюджет кадра и не замер новой реализации. Геометрия, FK, Qt/OCCT, выбор ветви при подготовке и предварительные проверки сюда не включены.

Сплайны обычно дешевле аналитической IK при вычислении кадра: шесть полиномов вместо геометрического решения. Но для одной модели выигрыш может быть практически несущественен, а подготовка и проверка дополнительной аппроксимации усложняются. Скорость альтернатив на нашей машине нужно измерять; опубликованные микросекунды Ruckig или IK-Geo не заменяют этот замер.

## Рекомендация и границы уверенности

Основное представление движения — исходная параметрическая поза TCP, закон времени и выбранное непрерывное решение аналитической IK. Подготовка не должна формировать плотную последовательность углов только ради последующей линейной интерполяции. Данные полилинии для изображения траектории в сцене и данные проверки допустимости могут существовать отдельно.

Приоритетный следующий эксперимент, если пользователь разрешит реализацию: измерить полный расчёт одной отображаемой позы через существующую геометрию и аналитическую IK на заранее согласованной конфигурации; проверить непрерывность и воспроизводимость при произвольном времени. Затем отдельно определить стоимость предварительной проверки всего пути. Не подменять это простым отключением плотного валидатора.

Не доказаны: точное время Generate после изменений; максимальная стоимость кадра; отсутствие особенностей по всему конкретному подводу; достаточность фиксированного числа проверочных точек. Число 16 не получило математического основания и не является рекомендацией этого обзора.

Прочитано локальное руководство D:/Qt/QtProjects/manuals/KUKA/KUKA Robot Programming 2 KSS 8.2.pdf, страницы 59 и 64–65: режимы ориентации CP различаются, включая постоянную ориентацию и преобразование углов запястья. Это дополнительно ограничивает вывод: предложенное представление описывает нашу заданную кинематическую анимацию, но не доказывает тождество внутреннему интерполятору KUKA. Закрытые CAM-пакеты не объявляются использующими конкретный алгоритм без опубликованного подтверждения.
